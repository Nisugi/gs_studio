Reviewed working tree at `54b58e4`. Existing untracked `canine/` and

## Bugs and quality regressions

### P1: GPU atlas admission can accept creatures that never render

`field_gpu_stage.rs:659` admits by total pixel area. `field_gpu.rs:676`
uses shelf packing with two pixels of padding on each edge. Three distinct
1024-square images pass the 85% area budget, but only one fits: two padded
1028-wide cells exceed the 2048-wide atlas, and two rows also exceed its height.

The GPU upload path resets and retries, but still cannot fit this frame.
Missing slots receive zero UV extent (`field_gpu.rs:1154`). By then
`StageGpu::push` already returned true, so the caller suppressed its fallback.
The creature disappears; a fallback must be decided before committing its draw.

Use an exact reservation plan shared by admission and upload, or multiple atlas
pages. Do not solve this by reducing image resolution. Test differently sized
layers, padding boundaries, repeated keys, and repacks after animation.

### P2: GPU puppet conversion removes outlines, including boss outlines

`field_gpu_stage.rs:768` builds alpha from `SkinSurface::texel` coverage rather
than the complete skin image. `skin.rs:804` draws the boss/outer contours even
where surface coverage is zero; `texel` correctly returns None there. The GPU
shader discards zero-alpha pixels, and the original skin is not drawn afterward.

Reproducer: humanoid, default pose, boss outline, 300-pixel camera produced an
88x231 skin with 3,574 visible pixels having no surface texel. Those pixels are
lost by the GPU conversion. Preserve the complete skin coverage and distinguish
decorative contour pixels from surfaces that should receive lighting.

### P2: Dead puppets receive the sprite corpse tint a second time

`skin.rs:621,664` already builds dead-body colors and blends texture toward
`BODY_DEAD`. `field_gpu_stage.rs:673` then assigns every dead layer the sprite
`DEAD_TINT` of 0.155. `field_gpu.wgsl:845` multiplies both base and albedo by it.
GPU corpses therefore become substantially darker than the existing skin path.

Keep sprite tinting, but give already dead-colored puppet skins unit tint.
Verify wounded and textured corpses as well as plain ones.

### P2: Lights beyond the GPU limit can lose their visible representation

`field_gpu_stage.rs:626` gives moons first claim on eight total light slots,
then takes only the remaining scene lamps. `field_lights.rs` suppresses every
torch and wisp's CPU drawing whenever the GPU frame is active, including lamps
that were never admitted. With two moons, the seventh scene torch can disappear.

Track which lamp IDs actually entered the pass and preserve representation for
the others. A full lighting solution needs explicit overflow handling; simply
raising the limit increases worst-case fragment work. There is no universal
free solution for arbitrarily many interacting lights.

### P2: Atlas padding is not cleared when slots are reused

`field_gpu.rs:760` uploads only each image's interior. Resetting the shelves and
slot maps does not clear the texture. A newly reserved gutter may contain pixels
from a previous occupant. Linear samples at image boundaries can therefore read
stale color/alpha. The padding guarantee in the file's comment is not maintained
after repacking.

Upload transparent gutters around each new allocation, or clear the atlas when
repacking. Test reuse with opaque edge pixels and contrasting old/new occupants.
This conclusion follows from allocation/upload code; no screenshot repro was
performed for this finding.

### P2: Texture dimensions do not establish UV compatibility

`studio/editor/texture.rs:757` and the client texture loader in
`creature_puppet.rs:1335` validate dimensions only. A rig edit can change patch
rows, seams or packing while keeping sheet width/height unchanged. Such a stale
sheet is silently accepted.

Reproducer: increasing one humanoid torso station's width by 0.1% changes its
`UvLayout`, but both layouts remain 958x981. This demonstrates the missing
identity check, not necessarily a large visible defect from that small edit.

Export a versioned UV-layout fingerprint with paintings, sheets and normals;
check it during build, load and publish. Hash the actual layout/geometry inputs,
not merely the source filename or texture dimensions. This costs no per-frame
rendering work.

## Performance opportunities that preserve quality

These are code-supported candidates, not measured before/after speedups.

1. **Separate geometry caches from lighting caches.** Backdrop/sprite keys in
   `field_gpu_stage.rs:612,701` include the relit texture ID. Every replacement
   lighting texture can trigger new geometry construction, map decoding and
   downsampling even though the camera/shape/depth maps did not change. Key
   geometry by asset revision, camera and size; update color independently.
   Split GPU upload identity too, so unchanged geometry is not re-uploaded.

2. **Bound caches by bytes and use actual recency.** The stage conversion cache
   retains 96 entries FIFO, not a byte budget or LRU. A 1408x752 backdrop's float
   geometry plus copied lit RGBA is about 20 MiB before other shared allocations.
   Different lighting revisions need not each own identical geometry. Track
   live CPU/GPU bytes and evictions; retaining useful current data improves
   stability without reducing image quality. `LightState::by_lit` also grows on
   every relight until lighting is disabled; retire obsolete texture IDs.

3. **Build fallback representations lazily.** `pose_puppet_with` unconditionally
   builds the old primitive draw list before constructing a skin. When a skin is
   present, `paint_figure` uses it; the old list is fallback work. Similarly,
   construct the CPU shadow caster on demand for the fallback lighting path.
   Preserve the public behavior through lazy storage rather than deleting it.

4. **Replace per-draw sampled skin hashing with stable revision IDs.**
   `field_gpu_stage.rs:748` allocates and hashes roughly 4 KB of sampled pixels
   on every skin draw to supplement a recyclable pointer. Assign identity once
   when the posed skin/surface is created. Include geometry identity explicitly.
   A pixel sample is neither a free lookup nor proof that geometry is unchanged.

5. **Profile and parallelize independent CPU relight work with a bounded pool.**
   The relight worker walks all layers serially (`creature_light.rs:693`). Layer
   outputs are independent after their inputs are gathered. Preserve output
   arithmetic/order per layer, avoid nested thread oversubscription, and compare
   bytes/golden output. Large backdrops and cold scene changes are better targets
   than adding threads to tiny cards.

6. **Keep shadow culling conservative.** The existing depth-slab optimization
   is the right kind of gain: avoid samples proven irrelevant rather than reduce
   sample count. A conservative light/caster or screen-tile candidate list may
   reduce the remaining all-layer traversal. Include out-of-tile shadow casters;
   visible-object-only culling would change shadows.

These are one-run warmed averages on the discrete AMD GPU. They are useful
directionally, not an FPS promise. The benchmark draws `Piece::Everything` once;
the app uses a backdrop callback plus per-creature callbacks and also performs
CPU posing, rasterization, cache conversion, atlas updates and egui work.

The benchmark's "8 torches + 2 moons" case actually supplies ten lights to an
eight-light limit. The last two torches are truncated; its label overstates the
work measured. Its crowd case reuses two creature images, so it does not stress
eight unique atlas allocations or independently animated skins.

## Pipeline additions with high value

- **Asset provenance manifest:** source silhouette hashes, view type/landmarks,
  rig and builder versions, pose set, clothing kit, UV layout fingerprint,
  paintings and normal-map versions. Make stale derived assets detectable.
- **Transactional saves/publication:** rig and pose source files still use
  direct `fs::write`. Write/validate sibling temporary files then replace;
  publish a validated staging set so clients never see mixed revisions.
- **Automated visual parity cases:** contours, boss markings, corpses, wounded
  skins, lamps over capacity, atlas repacks, camera changes, and both GPU modes.
  Existing topology and lighting golden tests do not cover the integration bugs.
- **Production-path benchmarks:** cold/warm scenes, unique animated skins,
  breathing, flinch/death transitions, lighting changes, and atlas pressure.
  Record p50/p95/p99, CPU work, uploads, cache misses, and memory alongside GPU
  timings. Keep deterministic frames for visual comparisons.
- **Backdrop geometry integration:** `StageGpu::begin` always uses
  `ground_geo`; the prototype loads actual backdrop depth and normal maps.
  The shader already samples a geometry texture, so consuming offline-authored
  maps can improve surface lighting without additional per-pixel texture samples.
  Decode/cache them on load, with the flat-ground representation as fallback.
- **Overlay geometry:** wounds/status overlays still draw after the GPU body
  pass. Map their pixels to base depth/normals so local light and weather agree
  with the body. This is a quality feature with real potential runtime cost,
  not a guaranteed free improvement.
- **Executable release gates:** the repo has useful tests, an all-family audit,
  goldens and a GPU bench, but no checked-in `.github` workflow was present.
  Wire deterministic checks into the actual CI/release process and use the
  approved `review.tsv` state as part of publication validation.

Recommended order: atlas correctness and skin parity first; then cache/geometry
separation and production measurements; then provenance and release gates;
then backdrop/overlay integration. Do not lower image size, shadow samples or
pose fidelity to hide redundant work.
